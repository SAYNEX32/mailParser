# Спецификация: Парсер почты Gmail/Mail.ru с интеллектуальной классификацией писем

## 1. Обзор

Система предназначена для автоматического сбора, парсинга и классификации входящих писем из Gmail и Mail.ru. Основная задача — разделение потока входящей корреспонденции на четыре категории: **Важные**, **Полезные**, **Спорные** (требующие внимания/уточнения) и **Спам**. Система должна быть расширяемой, с возможностью использования как эвристических правил, так и ML-моделей.

## 3. Модуль подключения к Gmail

### 3.1. Аутентификация

Gmail API требует **OAuth 2.0**. Процесс настройки:

1. Создать проект в Google Cloud Console.
2. Включить Gmail API.
3. Создать OAuth 2.0 Client ID типа **Desktop app**.
4. Настроить OAuth consent screen со scope `https://www.googleapis.com/auth/gmail.readonly` (или `gmail.modify`, если требуется проставление меток).
5. Получить refresh token через локальный OAuth-флоу или Google OAuth Playground.

**Необходимые scope:**
- `https://www.googleapis.com/auth/gmail.readonly` — только чтение.
- `https://www.googleapis.com/auth/gmail.modify` — чтение + управление метками (если система будет маркировать письма в Gmail).

**Конфигурация:**
```json
{
  "client_id": "YOUR_CLIENT_ID",
  "client_secret": "YOUR_CLIENT_SECRET",
  "refresh_token": "1//..."
}
```

### 3.2. Получение писем

Использовать метод `users.messages.list` с параметрами:
- `q` — поисковый запрос (например, `is:unread` или `after:2025/01/01`).
- `maxResults` — лимит на batch.

Для каждого `message_id` вызывать `users.messages.get` с `format="full"` для получения тела и заголовков.

**Библиотека:** `google-api-python-client` + `google-auth-oauthlib`.

## 4. Модуль подключения к Mail.ru

Mail.ru **не предоставляет публичного OAuth API для чтения почты** в том же виде, что Gmail. Доступ осуществляется через **IMAP** с использованием **пароля для внешнего приложения**.

### 4.1. Получение пароля

1. Войти в веб-интерфейс Mail.ru.
2. Перейти: **Все настройки → Безопасность → Пароли для внешних приложений**.
3. Создать новый пароль (обычный пароль от ящика не подойдёт).

### 4.2. Параметры IMAP

| Параметр | Значение |
|----------|----------|
| Сервер IMAP | `imap.mail.ru` |
| Порт | `993` |
| Шифрование | `SSL/TLS` |
| Аутентификация | Логин (полный email) + пароль для внешнего приложения |

**Библиотека:** `imaplib` (stdlib) или `aioimaplib` для асинхронной работы.

### 4.3. Получение писем

```python
import imaplib
mail = imaplib.IMAP4_SSL("imap.mail.ru", 993)
mail.login("user@mail.ru", "app_password")
mail.select("INBOX")
status, messages = mail.search(None, "UNSEEN")
```

Затем для каждого ID вызывать `fetch` с `(RFC822)` для получения полного письма.

## 5. Модуль парсинга

### 5.1. Библиотеки

- **Python stdlib `email.parser`** — надёжный парсинг MIME-структуры, извлечение заголовков и тела.
- **`emailparser`** (PyPI) — лёгкая альтернатива для извлечения структурированных данных из `.eml`.
- **`email-utilities`** — конвертация HTML-тела в читаемый текст.

### 5.2. Извлекаемые поля

| Поле | Источник |
|------|----------|
| `message_id` | Gmail API / IMAP UID |
| `from` | Заголовок `From` |
| `to` | Заголовок `To` |
| `subject` | Заголовок `Subject` |
| `date` | Заголовок `Date` |
| `body_text` | Декодированное тело (plain text) |
| `body_html` | HTML-версия (если есть) |
| `attachments` | Метаданные вложений (имя, тип, размер) |
| `headers_raw` | Полные заголовки для анализа |

### 5.3. Нормализация

Привести все письма к единой структуре (dataclass или dict) независимо от источника.

## 6. Модуль классификации

### 6.1. Категории

| Категория | Описание | Примеры |
|-----------|----------|---------|
| **Важные** | Требуют немедленного действия или ответа | Письма от руководителя, счета, юридические уведомления, срочные запросы |
| **Полезные** | Содержат ценную информацию, но не срочны | Рассылки по подписке, уведомления о событиях, информационные дайджесты |
| **Спорные** | Неоднозначные: могут быть важными, но требуют проверки | Незнакомый отправитель с «деловым» предложением, письма с грамматическими ошибками от «банка», письма с подозрительными вложениями |
| **Спам** | Явно нежелательная корреспонденция | Реклама без подписки, фишинг, мошенничество |

### 6.2. Гибридный подход

Рекомендуется **двухуровневая классификация**:

**Уровень 1: Эвристические правила (rule-based)**

Быстрые, интерпретируемые, не требуют обучения.

| Правило | Категория |
|---------|-----------|
| Отправитель в белом списке (контакты, известные домены) | Важные / Полезные |
| Отправитель в чёрном списке | Спам |
| Наличие слов «срочно», «важно», «требуется ответ» в теме | Важные |
| Наличие подписки (List-Unsubscribe header) | Полезные (если легитимно) |
| Отправитель не в контактах + ссылка на подозрительный домен | Спорные |
| Совпадение с известными спам-паттернами (тема капсом, множество восклицательных знаков) | Спам |
| Письмо содержит вложение `.exe`, `.scr`, `.js` от незнакомого отправителя | Спорные → Спам |

**Уровень 2: ML-модель (опционально)**

Для повышения точности можно добавить классификатор на основе:
- TF-IDF + Logistic Regression / SVM (быстро, интерпретируемо).
- Transformers (RuBERT / multilingual BERT) для русского и английского текста.

Модель обучается на размеченном наборе писем. При отсутствии разметки можно начать с правил, накапливая данные для обучения.

### 6.3. Признаки для классификации

- **Метаданные:** отправитель (адрес, домен, display name), наличие SPF/DKIM/DMARC (если доступно из заголовков), время отправки.
- **Тема:** длина, наличие ключевых слов, регистр, пунктуация.
- **Тело:** текст, ссылки (домены), вложения.
- **Поведенческие:** частота писем от отправителя, история взаимодействия (если отслеживается).

### 6.4. Обработка «Спорных»

Письма категории «Спорные» не должны автоматически удаляться или помечаться как спам. Рекомендуется:
- Помещать в отдельную папку/метку.
- Формировать ежедневный дайджест для ручного просмотра.
- Запрашивать обратную связь (пользователь подтверждает: спам или нет) для дообучения модели.

## 7. Выходные данные

### 7.1. Формат JSON

```json
{
  "source": "gmail",
  "message_id": "18d1e2f3...",
  "from": {"name": "Иван Петров", "email": "ivan@company.com"},
  "subject": "Срочно: согласование договора",
  "date": "2026-10-27T10:30:00Z",
  "body_text": "...",
  "classification": {
    "category": "important",
    "confidence": 0.95,
    "method": "rules",
    "reasons": ["sender_in_whitelist", "subject_contains_urgent_keyword"]
  }
}
```

### 7.2. Хранение

- **SQLite** для локального использования / прототипа.
- **PostgreSQL** для продуктивной нагрузки.

Схема таблицы:
```sql
CREATE TABLE emails (
    id SERIAL PRIMARY KEY,
    source VARCHAR(10),
    message_id VARCHAR(255) UNIQUE,
    from_email VARCHAR(255),
    from_name VARCHAR(255),
    subject TEXT,
    body_text TEXT,
    received_at TIMESTAMP,
    category VARCHAR(20),
    confidence FLOAT,
    method VARCHAR(20),
    created_at TIMESTAMP DEFAULT NOW()
);
```

## 9. Этапы реализации

| Этап | Задачи | Результат |
|------|--------|-----------|

| **5. Хранение** | SQLite/PostgreSQL, запись результатов | Сохранение и запросы |
| **6. (Опционально) ML** | Сбор разметки, обучение модели, интеграция | Гибридная классификация |

## 10. Ограничения и риски

| Риск | Митигация |
|------|-----------|
| Gmail API rate limits | Использовать `maxResults`, кэширование, batch-запросы |
| Mail.ru может изменить IMAP-политику | Мониторинг, fallback на пересылку через SMTP |
| Ложные срабатывания правил | Категория «Спорные» как буфер, ручная проверка |
| Отсутствие разметки для ML | Начать с правил, собирать обратную связь |
| Безопасность credentials | Хранить в `.env`, не коммитить в git, использовать secret manager в prod |
